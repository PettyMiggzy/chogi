# ChogiPayroll deep audit — 2026-05-08

**Scope.** `contracts/ChogiPayroll.sol` (primary), `contracts/ChogiSwapBurner.sol` (caller of `notifySwapFee`), `contracts/ChogiLabSubjects.sol` (referenced via `labSubjectsNft` slot), and the underlying `$CHOGI` ERC-20 they all transfer.

**Status of recommendations.** Per project decision on 2026-05-08, **no Solidity edits or redeploys are planned at this time**. This document is a record of findings only. Do not treat the "recommendation" subsections as a TODO.

**Severity legend.** Critical / High / Medium / Low / Gas-or-style.

---

## 1. High-severity findings

### H-01 — `notifySwapFee` is push-trust, not pull-authoritative

`ChogiPayroll.notifySwapFee(amount)` only checks `msg.sender == swapBurner`, increments `totalSwapFees`, and folds `amount` into `accRewardPerWeight`. It does **not** call `transferFrom`. It trusts that `ChogiSwapBurner._routeSkim` already sent the CHOGI before invoking the notify. On the happy path that holds, but:

1. If `swapBurner` is ever set to an address that calls `notifySwapFee` *without* first sending CHOGI, the accumulator inflates against CHOGI that does not exist in the contract. Subsequent `claim` / `unstake` will revert with `TransferFailed` once float is exhausted.
2. `_routeSkim` does `transfer` then a low-level `.call("notifySwapFee(uint256)", …)` and discards the boolean (`ok; // ignore`). If the notify reverts (paused doesn't apply — `notifySwapFee` is not gated by `whenLive` — but reentrancy or future bytecode changes could revert), the CHOGI sits in Payroll uncredited. A future stake will absorb it as float, silently.
3. `notifySwapFee` is not gated by `whenLive`. Pausing Payroll does not break the swap path — acceptable — but means a paused Payroll still mutates `accRewardPerWeight`. Document this.

### H-02 — `_addToPool` strands fees and donations during zero-TVL windows

```solidity
function _addToPool(uint256 amount) internal {
    if (amount == 0) return;
    if (totalWeighted == 0) {
        _pendingPreStake += amount;
        return;
    }
    accRewardPerWeight += (amount * ACC_PRECISION) / totalWeighted;
}
```

`_pendingPreStake` is only ever drained inside `stake()`, where it is folded into the accumulator *before* the new staker's `rewardDebt` is anchored. So the **first** post-zero-TVL staker captures none of the bucket directly, but they are also the only weight in the pool until a second staker arrives — meaning every reward folded between their stake and the next stake accrues entirely to them. A whale who times the first stake after a TVL=0 window collects the entire `_pendingPreStake` plus all yield until a second staker arrives.

A second strand of the same issue: `unstake` for the *last* staker (the one whose exit takes `totalWeighted` to 0) calls `_addToPool` for the recycled CHOGI term fee **after** decrementing `totalWeighted`. That recycle therefore parks in `_pendingPreStake` and is captured by the next first-stake event (same dilution as above).

### H-03 — Reward solvency is an off-chain assumption

Payroll tracks principal (`assets[token].totalDeposited`) but not the sum of pending rewards. `accRewardPerWeight` can grow faster than the float (CHOGI balance minus principal) when `weightPerWei` for non-CHOGI assets is set generously — e.g. `WMON · 200K:1` grants 200,000 weight units per WMON wei while paying only the flat 10K CHOGI stake fee. If float runs dry, individual `claim` / `unstake` calls revert on the CHOGI reward `transfer` and stakers cannot exit. The contract has no degraded mode (no "claim what's available, defer the rest").

### H-04 — `whitelistAsset` allows retroactive `weightPerWei` changes without timelock or floor

The contract is structured so existing positions snapshot `weight` at stake time, which protects them from later weight changes. But:

1. There is no minimum `weightPerWei` or maximum cap, so the owner can drop a token's weight to 0 (DoS new stakes for that token) or pump it without warning.
2. There is no per-asset timelock, so weight changes are atomic and frontrunnable by an admin-controlled wallet.
3. `delistAsset` only flips `accepted = false`; combined with no removal from `assetList`, an owner can whitelist at a favorable ratio, allow an insider stake, then delist — leaving the insider with the share-of-pool while no one else can stake at that ratio.

### H-05 — `CHOGI` is a `constant` address with no migration path and no SafeERC20 wrapper

```solidity
IERC20 public constant CHOGI = IERC20(0x5E1b1A14c8758104B8560514e94ab8320e587777);
```

Three of the contracts hardcode this address. If the CHOGI token is ever upgraded, taxed, paused, or fee-on-transfer behavior is added, every Payroll accounting assumption breaks. The current `IERC20` interface uses a strict `bool` return convention with no SafeERC20 fallback, so a non-standard return becomes a `TransferFailed` revert for every staker.

## 2. Medium-severity findings

### M-01 — `claim` / `unstake` ordering is correct on the active-flag check; no real issue, recorded for completeness.

### M-02 — `whitelistAsset` does not bound `weightPerWei` or pin CHOGI

No lower bound (`weightPerWei = 0` is accepted, which DoSes new CHOGI stakes via `WeightTooLow`). No CHOGI pin, so the CHOGI numeraire can be moved away from 1e18.

### M-03 — Single-step `transferOwnership` across all three contracts

A mistyped target is irreversible. Standard fix is a two-step accept pattern.

### M-04 — `delistAsset` does not swap-and-pop `assetList`

`assetCount` grows monotonically. Frontends that iterate `assetList` (admin and likely the public payroll page) eat the gas / RPC cost of iterating dead entries.

### M-05 — `sweepLooseTokens` mixes `require` strings with custom errors

Style inconsistency. Switch the one `require(bal >= reserved + amount, "would touch user funds")` to a custom error.

### M-06 — `_pendingPreStake` is denominated in CHOGI but is not visible in `poolMeter` or any view

Float-monitoring tools that read `poolMeter().floatBalance` cannot tell that some of that float is earmarked for the next stake's accumulator fold.

### M-07 — Cross-contract reentrancy is contained today, but `_routeSkim` -> low-level call pattern is fragile if CHOGI ever becomes a hook token (ERC-777-like).

## 3. Low / informational

- L-01 — `Asset.weightPerWei` is `uint128`; product fits in `uint256` and divides by `1e18`. No overflow path.
- L-02 — `Position.amount` and `Position.weight` are `uint128` with unchecked downcast in `stake()`. Safe up to ~3.4e38; flagged for completeness.
- L-03 — `commitDays` and `maxTermBps` are immutable post-deploy. Intentional.
- L-04 — `donate` is `whenLive`; `notifySwapFee`, `claim`, `unstake` are not. The `whenLive` boundary is therefore narrower than "all writes". Document.
- L-05 — `quoteUnstake` returns `reward = vested ? pending : 0`; `pendingReward` returns the raw pending. Frontend should pick one.
- L-06 — `setSwapBurner(address(0))` is allowed and silently disables the swap-fee notify pipeline. Probably a kill switch; undocumented.
- L-07 — `_patronList` is append-only; large patron sets become expensive to iterate off-chain.

## 4. SwapBurner-side issues

### SB-01 — `_routeSkim` ignores the `notifySwapFee` boolean (`ok; // ignore`)

If the notify reverts after the CHOGI transfer succeeded, the swap completes from the user's perspective and Payroll has uncredited float. Recommendation withheld per project decision.

### SB-02 — `setPayroll(_payroll, _payrollBps)` does not validate that `_payroll` is a contract

A mistyped EOA target receives every per-swap CHOGI skim with no possibility of `notifySwapFee` succeeding (no code at address). Funds drain to the wrong address. A `_payroll.code.length > 0` guard would prevent this.

### SB-03 — `quote(isBuy=false, expectedOut)` returns `burned = 0`

The burn happened on the input side, but frontends that surface the per-swap burn from `quote` will display zero on sells, which is misleading to users.

### SB-04 — `refreshRouterApproval` is permissionless

Re-approves a hardcoded router for max. Acceptable because the router address is `constant`, but worth re-confirming on every redeploy.

## 5. LabSubjects interaction with Payroll

- `Payroll.labSubjectsNft` is set via `setLabSubjectsNft` and cast as `IERC721Like`, but the Payroll contract never reads from it. Dead code today.
- `ChogiLabSubjects.mintByBurning` calls `transferFrom(msg.sender, DEAD, cost)`. No interaction with Payroll. Independent.
- `ChogiLabSubjects.soulbound` toggle is owner-controlled and does not clear `_tokenApprovals`; flipping soulbound off restores prior approvals. Contained.

## 6. System-level observations

1. **Trust topology.** Single owner key controls pause, whitelist, weight, swap burner address, lab subjects address, ownership transfer, sweep stranded fees, sweep loose tokens. Compromise = ability to add malicious tokens, change weights, redirect swap-fee skim (`setSwapBurner(0)`), or drain stranded balances. A multisig with per-action timelocks would mitigate.
2. **CHOGI is the unit of account, the reward token, and the fee token.** Single point of failure across all three contracts. No fallback reward token.
3. **Reward solvency invariant** (most important off-chain monitor): at all times, `CHOGI.balanceOf(payroll) >= assets[CHOGI].totalDeposited + sum(pending rewards across all active positions)`. The contract enforces only the principal half (`totalDeposited`). Pending rewards are bounded only by the float that has been added via fees / donations / skim.
4. **Emergency withdraw.** Stakers can `unstake` and `claim` even when paused (no `whenLive` on those paths). Stakers are not held hostage by a pause. Confirmed safe.
5. **Block-timestamp dependence.** `cliffSec`, `lockSec`, `feeBps` derive from `block.timestamp`. Standard ~15s caveat. With cliffs in days, immaterial.

## 7. Repo-vs-chain divergences (verify cycle, 2026-05-09)

When pushing verification to MonadScan/SocialScan, the repo source for `ChogiSwapBurner.sol` no longer matched the deployed bytecode. The deployed source had to be pulled from Sourcify to verify.

**Divergence:** `ChogiSwapBurner._routeSkim` `minRouterOut` calculation
- Deployed (commit prior to `cf18ec6`): ceil division — `(minOutToUser * 10000 + denom - 1) / denom`
- Repo (`main` @ `cf18ec6`, "fix swap slippage default", 2026-05-08): floor division — `(minOutToUser * 10000) / denom`

**Impact:** the repo change is a comment + 1-wei rounding adjustment defended by the post-skim check. Not a security issue. But it means the repo is ahead of chain by one functional change on this contract, and any future v2 redeploy must consciously decide which version to ship. Flag so it doesn't get lost.
